D-01Critical

Вебхук оплаты без проверки подписи

Сценарий. Оплата подписки «Премиум».

Шаги. Отправить на /webhooks/pay тело успешного платежа без валидной подписи.

Ожидалось. 401/403, подписка не меняется. Получено. 200, статус Premium, повтор того же события выдаёт вторую запись.

D-02Critical

Поиск блокирует цикл aiogram

Сценарий. Поиск объявлений по запросу.

Шаги. 20 одновременных запросов «квартира, центр».

Ожидалось. Ответы без паузы бота. Получено. Хендлер вызывает синхронный Session.execute, остальные апдейты ждут 2–4 с.

D-03Critical

Платное объявление видно до подтверждения оплаты

Сценарий. Публикация объявления в топе.

Шаги. Создать объявление, открыть поиск, не завершая оплату.

Ожидалось. Черновик скрыт до успешного платежа. Получено. Карточка сразу в выдаче с меткой «Топ».

D-04Major

Ключи FSM в Redis без TTL

Сценарий. Мастер подачи объявления, пользователь уходит на шаге 3.

Шаги. Начать сценарий, оборвать чат, проверить ключи fsm:* через сутки.

Ожидалось. Истечение сессии. Получено. Ключи копятся без срока жизни.

D-05Major

Сессия SQLAlchemy не закрывается при ошибке

Сценарий. Редактирование объявления с невалидным фото.

Шаги. Отправить повреждённый файл, повторить 50 раз, смотреть пул соединений.

Ожидалось. rollback и закрытие сессии. Получено. Исключение до commit, сессия остаётся открытой, пул исчерпывается.

D-06Major

Отмена подписки не останавливает продление

Сценарий. Отмена автопродления.

Шаги. /premium_cancel, дождаться даты продления на стенде.

Ожидалось. Списание не уходит. Получено. Статус «отменена», вебхук renewal всё равно активирует период.

D-07Major

Повторный платёж создаёт вторую подписку

Сценарий. Пользователь дважды подтверждает одну оплату.

Шаги. Два одинаковых event_id на вебхук и повторный клик «Оплатить».

Ожидалось. Идемпотентность, один период. Получено. Две активные подписки, двойной доступ.

D-08Minor

Ошибка API без корреляции

Сценарий. Сбой поиска при недоступной БД.

Шаги. Остановить PostgreSQL, отправить /search.

Ожидалось. Понятное сообщение и идентификатор запроса в логе. Получено. «Произошла ошибка», в логе traceback без id пользователя и апдейта.

Код-ревью бэкенда

Выборочный разбор репозитория демо-стенда. Не полный аудит безопасности.

Async: блокирующие вызовы в хендлерах

В search и publish используются синхронные вызовы SQLAlchemy и requests внутри async-хендлеров aiogram и FastAPI. Под нагрузкой это останавливает цикл событий. Нужны async-сессии (или to_thread как временная мера) и отказ от блокирующего HTTP в обработчиках.

Сессии БД: утечки, commit и rollback

Зависимость get_session в FastAPI не закрывает сессию в finally. В хендлерах aiogram сессия создаётся вручную и при исключении не делается rollback. Это совпадает с D-05 и рискует исчерпать пул PostgreSQL.

Redis: TTL и ключи FSM

Хранилище состояний пишет ключи fsm:{user}:{chat} без expire. Кэш выдачи поиска тоже без TTL. Нужно задать срок жизни сценария (например 24 часа), префикс по окружению и политику вытеснения для кэша.

Обработка ошибок

Глобальный error handler глотает исключения и отвечает одной фразой. Нет идентификатора запроса, нет различия между ошибкой пользователя и сбоем инфраструктуры. Для FastAPI стоит отдать стандартизованный JSON с кодом, для бота — короткое сообщение и запись в лог с корреляцией.

Учётные данные в коде и в конфиге окружения

В репозитории найдены зашитые токены платёжного шлюза и строка подключения к БД в исходниках. Файл переменных окружения попадает в образ Docker. Нужно вынести значения в секреты оркестратора, добавить проверку в CI, ротировать уже засвеченные ключи.

Платежи и подписки

Проверка вебхуков, повторной оплаты, отмены и продления на демо-стенде.

Вебхуки

Подпись не проверяется (D-01). Нет журнала обработанных event_id, повтор того же события применяется снова. Нужна проверка подписи, идемпотентный ключ и ответ 2xx только после устойчивой записи.

Повторный платёж

Второй клик «Оплатить» и повтор вебхука создают вторую подписку (D-07). Нужна уникальность платежа и защита кнопки до завершения первого запроса.

Отмена

/premium_cancel меняет статус в БД, но флаг автопродления у провайдера не снимается (D-06). Отмена должна быть транзакцией: провайдер, затем локальный статус, с повтором при сбое.

Продление

Событие renewal не сверяется с флагом отмены и не привязано к текущему периоду. Возможны двойное продление и доступ после отказа от подписки.

Короткий прогон поиска и публикации на демо-стенде. График схематичный, цифры вымышленные, это пример оформления.
